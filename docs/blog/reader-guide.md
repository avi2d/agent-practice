# Правила для статей

Эти правила задают язык, словарь и порядок разделов для каждой статьи в `docs/blog/`.
Существующие статьи переписываются по этим правилам после того, как владелец одобрит тон пробной статьи.
Статью читает человек со стороны, например рекрутер, который не пишет код.
Он должен понять из неё, какую проблему решает автор, к чему он стремится и как устроено его решение.

## Три слоя статей

| Слой | О чём статьи |
| --- | --- |
| Взгляды | позиция автора о работе с агентами: оркестрация, безопасность, проверки качества и другие темы |
| Инструменты | инструменты, которые автор создаёт и использует, и то, как он с ними работает |
| Результаты | принятые изменения и проекты, которые автор ведёт с помощью агентов |

Статья относится к одному слою и ссылается на статьи соседних слоёв.

## Язык

- Статьи пишутся на русском языке.
  Английские версии появятся после того, как будет написан слой результатов.
- Каждое предложение передаёт одну мысль и умещается в одну строку файла.
- Термин из словаря ниже объясняется при первом упоминании в статье.
- Вместо жаргона используется русское слово: «исправление», а не «фикс», «проверка», а не «чек».
- Число в статье даётся вместе с источником и датой, на которую оно посчитано.
- Текст статьи называет источник словами, а все ссылки стоят в разделе `## Ресурсы` в конце статьи.

## Словарь

| Термин | Что значит |
| --- | --- |
| кодовый агент | программа на основе языковой модели, которая сама читает код, запускает команды и вносит правки |
| модель | языковая модель, которая получает текст и пишет ответ, а агент построен вокруг неё |
| сессия | одна непрерывная работа агента над задачей, с журналом действий и итогом |
| контекст | весь текст, который модель видит в момент ответа: задача, файлы, история сессии |
| навык | записанная инструкция, которую агент загружает, когда задача её требует |
| оркестрация | запуск нескольких агентов, учёт очереди задач и сбор результатов в одном месте |
| репозиторий | хранилище кода проекта вместе с историей всех изменений |
| ветка | отдельная линия изменений в репозитории, которая не трогает основную, пока её не примут |
| PR | пул-реквест, запрос на изменение: предложение влить ветку в основную, которое можно обсудить и проверить |
| слияние | принятие PR, после которого изменение попадает в основную ветку |
| CI | непрерывная интеграция: сервер, который запускает проверки на каждый PR |
| проверка качества | автоматическое правило, которое не пропускает изменение, пока оно не выполнено |
| тест | программа, которая проверяет, что код делает то, что от него ждут |
| ревью | разбор изменения перед слиянием, человеком или отдельным агентом |
| секрет | пароль, ключ или токен доступа, который нельзя показывать в тексте и журналах |
| изоляция | запуск агента в среде, где ему доступны только нужные задаче файлы и сеть |

## Порядок разделов статьи

| Раздел | Что в нём |
| --- | --- |
| `## Проблема` | что ломается или мешает, простыми словами и на понятном читателю случае |
| `## Цели` | чего автор добивается, и какие тезисы служат каждой цели |
| `## Тезисы` | тезисы автора, каждый под своим заголовком, с основаниями и пробелами в них |
| `## Решение: <инструмент или правило>` | как устроено решение автора и какой тезис выполняет каждая его часть |
| `## Ресурсы` | все ссылки статьи: инструменты, документация, исследования, сообщество и соседние статьи |

Раздел без материала опускается, а его место не заполняется догадкой.
Число принятых PR и активность на GitHub в статью не входят.

Схема показывает ход работы там, где словами его проследить трудно.
Схема пишется на языке Mermaid, и на ней не больше блоков, чем помещается в один абзац текста.
Под схемой стоит подпись курсивом, которая начинается с номера схемы и говорит, что читатель должен из неё вынести.

Статья может содержать несколько тезисов.
Каждый тезис стоит в разделе `## Тезисы` под своим заголовком третьего уровня, например `### T01`.
Заголовок тезиса содержит только его код, чтобы ссылки вида `orchestration.md#t01` из [перечня тезисов](theses.md) продолжали работать.
Тезис открывает строка жирным шрифтом с меткой вида, а за ней идут позиция автора и её основания.

## Виды утверждений

Каждый главный тезис статьи открывает строка жирным шрифтом, которая начинается с одной метки вида, чтобы читатель отличал мнение от данных.
Остальные предложения тезиса идут без меток, и разделы `## Проблема`, `## Цели` и `## Решение` тоже пишутся без меток.

| Метка | Что за ней стоит |
| --- | --- |
| **Позиция автора** | мнение автора из его ответов, без замера |
| **Правило** | правило работы, которое автор соблюдает, и файл, где оно записано, в ресурсах |
| **Устройство** | как работает инструмент, и файл со строкой, где это описано, в ресурсах |
| **Измерение** | число из записи, с источником, датой и размером выборки |
| **Гипотеза** | предположение, которое ещё не проверено, и способ его проверить |

Позиция автора и гипотеза не выдаются за измерение.
Если источник не позволяет сделать вывод, статья называет этот пробел.

## Инструменты

Свои инструменты автора называются по имени и ведут на свой репозиторий.

| Инструмент | Что делает |
| --- | --- |
| [Orc](https://github.com/avi2d/orc) | ведёт очередь задач для агентов, запускает их и показывает ход работы в одном чате |
| [skills](https://github.com/avi2d/skills) | хранит инструкции для агентов в одном месте и доставляет их разным агентам |
| [Checks](https://github.com/avi2d/checks) | набор автоматических проверок, общий для нескольких репозиториев |
| [Subquo](https://github.com/avi2d/subquo) | показывает, сколько осталось от лимита платных подписок на агентов |

Продукт другой компании называется по своей роли, например «конвейер проверок» или «агент для ревью».
Статья не описывает компьютеры автора, их имена, адреса, папки и настройки, например ограничение времени на один вызов.

## Результаты

- Открытый проект называется по имени и ведёт на свой репозиторий или PR.
- Закрытый проект не называется и входит только в общие числа.
- Каждое общее число даётся вместе с датой и способом подсчёта.

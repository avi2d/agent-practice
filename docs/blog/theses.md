# Выбранные тезисы

Этот перечень ведёт к объяснению каждого выбранного тезиса.
Если у тезиса есть код, по нему можно открыть источник, основания и границы вывода.
Сама формулировка в перечне не объявляет тезис доказанным.

## Темы

### Оркестрация агентов

Принципы этой темы не имеют кодов, а [статья об оркестрации](orchestration.md#принципы) объясняет каждый.

- Работу ставят словами в одном месте.
- Задача заканчивается проверяемым результатом, а крупная делится на части.
- Каждый работник получает роль, а роль задаёт модель и reasoning effort.
- Машину и аккаунт выбирает система.
- Каждая задача работает в своём worktree, а система агентов в изолированной среде.
- Любую работу можно прервать и продолжить.
- Готово значит проверено.
- Ревью делает сильная модель другого семейства.
- Важное правило держит программа, а не инструкция.
- Внимание человека тратится только на решения.
- Кто делает merge, решают правила проекта и вид задачи.
- Состояние видно без захода в сессию агента.

### Автономия и контроль

Принципы этой темы не имеют кодов, а [статья об автономии](autonomy.md#принципы) объясняет каждый.

- Автономию задаёт цена ошибки, а не доверие к агенту.
- Внутри изолированной среды агент не спрашивает разрешения.
- Чем дороже ошибка, тем ближе решение к человеку.
- Критичные и рискованные операции ждут человека.
- Что считать критичным, решает список в коде, а не модель.
- Повторный сбой останавливает агента.

### Безопасность и секреты

Принципы этой темы не имеют кодов, а [статья о безопасности](security.md#принципы) объясняет каждый.

- Прочитанный текст не даёт полномочий.
- Границу строят в расчёте на обманутого агента.
- Граница одна и обводит систему агентов, а не каждого агента.
- На машине человека остаётся только то, что без неё не работает.
- Секрет получает инструмент, а не агент.
- Токен агентов открывает только их репозитории.
- Main защищает хостинг репозиториев, а не инструкция.
- Сеть закрыта, пока задача не назвала адрес.
- Среду проверяют по файлам, логинам, сети и ресурсам отдельно.
- Изоляцию проверяют изнутри.
- Границу не двигает тот, кого она держит.

### Проверки качества и мутации

Принципы этой темы не имеют кодов, а [статья о проверках качества](quality.md#принципы) объясняет каждый.

- Правило, которое можно проверить, держит программа.
- Gate отказывает, а не исправляет.
- Обход проверки тоже нарушение.
- Новое правило начинается с изменённых строк.
- Build, тест и проверка на месте отвечают на разные вопросы.
- Ожидаемый результат берут не из проверяемого кода.
- Тест сначала должен упасть.
- Тесты проверяет мутация, а не покрытие.
- Выжившего мутанта разбирают.
- Gate считает потерянные проверки, а не процент.
- Проверка смотрит только на то, чего коснулось изменение.
- Ревью проверяет то, что программа не выразит.
- Повторное замечание становится правилом в программе.

### Оценка агентов и навыков

Принципы этой темы не имеют кодов, а [статья об оценке](evaluation.md#принципы) объясняет каждый.

- Оценка измеряет систему на задачах, а не модель.
- Задачи берут из собственной работы.
- Задачи итоговой оценки не используют при настройке.
- Меняют одно, а остальное держат.
- Один запуск не даёт ответа.
- Вердикт выносит программа.
- Следование правилу и результат работы измеряют отдельно.
- Запись оценки не правят.
- Правило без прироста выключают.
- Правило включают для той модели, которой оно помогает.
- После смены модели оценку повторяют.
- Модель и reasoning effort выбирают тем же сравнением.
- Долю успеха читают вместе с ценой.

### Выбор модели и reasoning effort

Принципы этой темы не имеют кодов, а [статья о выборе модели](models.md#принципы) объясняет каждый.

- Модель выбирают по виду работы, а не по размеру изменения.
- Сильную модель тратят там, где ошибку не поймает проверка.
- Reasoning effort выбирают отдельно от модели.
- Выбор записан в правилах, а не делается перед запуском.
- Правило называет кандидатов по порядку, а не одну модель.
- Остаток квоты читает программа перед каждым запуском.
- Неизвестный остаток не считается свободным.
- Без подходящего кандидата задача ждёт.
- После повторного отказа проверок усиливают модель или reasoning effort.
- Каждый запуск записывает, почему выбрана эта модель.
- Правило меняют по записям, а не по рейтингу.

### Контекст и сжатие

- [**CTX01.**](context.md#ctx01) Автоматическое сжатие контекста можно поручать более дешёвой модели, сохраняя важные решения и ограничения.
- [**CTX02.**](context.md#ctx02) Единый порог сжатия для всех моделей составляет 150 тысяч токенов.
  Резерв для каждой модели равен размеру её окна за вычетом этого порога.
- [**CTX03.**](context.md#ctx03) Личное наблюдение за долгой сессией и её сжатиями.
- [**CTX04.**](context.md#ctx04) Контрольная точка для решения о продолжении, разделении или передаче долгой задачи.

### Документация, спецификации и комментарии

- [**R01.**](documentation.md#r01) README должен помогать незнакомому человеку понять назначение репозитория и начать работу.
- [**R02.**](documentation.md#r02) README должен направлять к подробностям, а не дублировать всю документацию.
- [**G01.**](documentation.md#g01) Инструкции для агента должны указывать границы работы и источники, а не подменять документацию проекта.
- [**G02.**](documentation.md#g02) Правила для агента должны быть проверяемыми там, где их может проверить программа.
- [**V01.**](documentation.md#v01) VISION задаёт назначение проекта, границы и компромиссы при выборе изменений.
- [**ADR01.**](documentation.md#adr01) ADR сохраняет принятое архитектурное решение, рассмотренные альтернативы и последствия для будущих изменений.
- [**DOC01.**](documentation.md#doc01) Документация описывает актуальное устройство и использование системы, а записи решений объясняют причины выбранного устройства.
- [**SPEC01.**](documentation.md#spec01) Спецификация задаёт проверяемое поведение до реализации, чтобы результат можно было сравнить с требованиями.
- [**SP01.**](documentation.md#sp01) В spec-driven development спецификация фиксирует требования, а устройство системы по возможности выражено в коде.
  Оба артефакта нужно поддерживать.
- [**SP02.**](documentation.md#sp02) Код выражает устройство и инварианты через имена, типы и структуру.
  Спецификация не должна дублировать каждую строку.
- [**SP03.**](documentation.md#sp03) Спецификацию поддерживают вместе с кодом: устаревшее описание может направить агента неверно.
- [**CM01.**](documentation.md#cm01) Сначала я выражаю смысл именем, типом или структурой, а не комментарием.
- [**CM02.**](documentation.md#cm02) Комментарий объясняет, какое ограничение исключает очевидный подход, или называет инвариант, который система типов не может выразить.
  Других комментариев в коде нет, а лицензионные заголовки остаются как условия лицензии.
  Обоснование, которому нужен абзац, хранит запись решения, а историю изменения хранит сообщение коммита.
